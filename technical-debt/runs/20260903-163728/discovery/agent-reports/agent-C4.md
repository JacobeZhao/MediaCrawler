# C4 Tests, Tooling, Documentation, And Operations

## Scope

Read-only inspection of repository-declared tests, build/tool configuration, docs, operations, generated-output policy, observability, and local/production parity. No service, browser, database, network, external tool, or protected content was accessed.

## Verification Inventory

- Fourteen flat `unittest` modules declare 91 test methods, using `IsolatedAsyncioTestCase`, mocks/fakes, temporary directories/SQLite, subprocesses, and `httpx.MockTransport`; there is no shared fixture layer.
- Documented broad gates are `compileall` and `unittest discover`; HTTP/browser checks are manual.
- The repository `.venv` launcher targets a missing interpreter. Fallback Python 3.12.13 reports 46 outcomes: 35 pass, 10 dependency import errors, and 1 dependent failure due absent SQLAlchemy, aiosqlite, and Playwright.
- Tests characterize lifespan (3), content repository (6), JustOneAPI executor (9), provider client (11), local executor (3), QR sessions (4), redaction (6), runtime env (14), service task DB (8), startup (4), supervisor (7), task manager (4), task service (11), and XHS replies (1).
- No CI/CD workflow, lockfile, lint/type/coverage configuration, container/build definition, frontend test system, or automated docs/API parity gate exists.

## Tools And Operations

`tools/` mixes imported runtime helpers (`crawler_util`, HTTP client, redaction, time, logging) with task submission, Markdown export, and external MySQL ETL CLIs. `ops/` owns Windows foreground startup, child supervision/restart/log rotation, cookie-file import, and operator guidance. Both launch modes converge on `start_xhs_service.py` and one Uvicorn process but depend on the broken local `.venv`. MySQL and account-import tools cross external/secret-bearing boundaries and were not executed.

## Documentation And Configuration

Root and topical docs coherently describe the application, architecture, API, task lifecycle, frontend, config, testing, operations, debt, and MySQL context, but freshness is manual. `pyproject.toml` and `requirements.txt` declare the same 13 runtime dependencies without a lock/parity gate. `.env.example` is incomplete relative to `Settings`, and package/runtime versions conflict. Static frontend assets are source, not generated output.

## Generated/Runtime Policy

Runtime/protected: `data/`, browser profiles, SQLite and sidecars, `.env`; generated: exports/logs/bytecode/test/type/build caches. None is disposable merely because ignored. `cache/` is active tracked source. `technical-debt/**` is generated by the workflow but durable project evidence.

## Observability And Parity

Current observability is local logs with supervisor rotation, health/readiness/version/status endpoints, task leases/heartbeats/checkpoints, persisted crawl events, and provider request audits with tested redaction. There is no metrics/tracing/alerting pipeline. Production is documented as a manual single-Windows-host deployment; no infrastructure/release artifact enforces it. Python 3.11 is selected by `.python-version`, `>=3.11` is allowed by metadata, and only an incomplete 3.12 fallback baseline ran.

## Evidence-Backed Gaps

1. Reproducible verification is blocked by a stale environment and unlocked dependencies.
2. Compile/tests and dependency parity have no automated clean-environment gate.
3. Static frontend and HTTP route integration lack automated behavior/accessibility smoke coverage.
4. Supervisor restart and account-import behavior lack bounded integration coverage.
5. Docs/config/API/version parity is manually maintained and already divergent.
6. Live XHS, JustOneAPI payload, and MySQL contracts require separately authorized controlled probes.
7. Configuration validation varies across import, launcher, schema, and provider layers.

All test/tooling/docs/ops files and directories were substantively classified. Missing CI, coverage, type checks, metrics, or live probes become target goals only when tied to an evidenced requirement.
